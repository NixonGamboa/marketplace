# E2E de navegador (T-22)

Runner Playwright que usa el **Chrome instalado** (`channel: 'chrome'`, o `E2E_CHROME_PATH`); no descarga navegadores. Dos contextos independientes (cliente en la PWA, personal en `/admin`) contra la API y Postgres reales del Preview de test. No hay mocks de auth, pedidos ni catálogo.

| Comando | Qué hace |
|---|---|
| `npm run e2e:selftest` | Guardas, saneado y lectura del ready; sin red, credenciales ni navegador (corre en `ci:check`) |
| `npm run e2e:check` | Solo lectura: `/api/health` = test/connected y PWA/admin en modo **real** (no demo) |
| `npm run e2e:smoke` | Crea **un** pedido propio y recorre cliente → recepción → pesos reales → entrega → comprobante/audit/enlaces |
| `node scripts/e2e-run.mjs full` | Smoke + suite completa: permisos, persistencia/nueva sesión, cierre/agotado, precio manipulado, doble envío, timeout posterior al commit, 401/429/503, offline/3G, sustitución/cancelación y catálogo editado |
| `npm run typecheck:e2e` | Tipos del runner |

## Condiciones de ejecución

### Quién genera el ready y dónde lo guarda

`scripts/e2e-ready.mjs` **no genera archivos**: exporta `parseReady` (lectura y validación) y `readyStamp` (huella del contenido). No hay un comando `npm run e2e:ready`. El orquestador genera el ready después de comprobar el deployment real y el reset/seed, y lo guarda en **`<raíz del checkout>/orquestacion-local/night-cloud-ready.json`**, fuera de Git. En el lote T-22/T-24 lo publicó el helper local privado `.claude/orquestacion/night-health.mjs`; su ruta de salida apuntaba al checkout aislado de T-22, ya retirado al cerrar el lote. No reutilizar ese helper sin adaptar y verificar el destino.

`scripts/e2e-run.mjs` lee esa ruta por defecto; `E2E_READY_FILE` permite indicar otra ruta explícita. El ready contiene URL/origen, SHA, deployment, modo real y confirmación fechada del reset/seed; no contiene contraseñas ni bypass. Publicarlo no ejecuta un reset: ambas verificaciones deben haberse completado antes. `check` no lo consume; `smoke` y `full` registran su consumo en `orquestacion-local/e2e-consumed.json`. Un archivo archivado o consumido no autoriza una nueva corrida con escrituras.

- `check`, `smoke` y `full` exigen `orquestacion-local/night-cloud-ready.json` (lo publica root con el Preview identificado, en modo real y con el seed limpio). El launcher toma de ahí `BASE_URL`/`AUTH_ORIGIN` y el SHA. `smoke` y `full` **consumen** cada ready una sola vez: otra corrida con escrituras requiere reset y ready nuevos. `full` requiere T-20/T-21 integrados y confirmados por root.
- Para ME-01..04 existe el modo adicional `dataMode: "isolated-preserved-baseline"`: copia Neon de dev, sin reset ni seed. Antes de lanzar cualquier escenario cloud, el launcher ejecuta el helper Node independiente que root aprobó mediante `E2E_ISOLATED_PREFLIGHT_HELPER` y `E2E_ISOLATED_HELPER_SHA256`; su dependencia SQL exige además `MAUI_ME_DATABASE_HELPER_SHA256` y el módulo puro `MAUI_ME_BASELINE_MODULE_SHA256`. El helper reconsulta SHA/ref/alias y SQL; su estado verificado y su baseline privada son independientes del ready. La metadata Neon autenticada debe refrescarse por MCP hace menos de cinco minutos; la comprobación SQL/deployment debe tener menos de un minuto. El ready debe coincidir con deploymentId, SHA, origen, clone, count/digests y `MAUI_ME_RUN_ID` autorizados, y no contiene `seedClean` ni resetAt. Se rechazan tanto stamps como runIds consumidos aunque cambie el texto. Las cuentas/pedidos previos se conservan; solo se crean pedidos propios nuevos y se devuelven los fixtures. El modo legacy y sus rechazos siguen vigentes.
- La suite ME completa exige `SMOKE_ME_CUSTOMER_PHONE`/`SMOKE_ME_CUSTOMER_PASSWORD` y `SMOKE_ME_SECOND_CUSTOMER_PHONE`/`SMOKE_ME_SECOND_CUSTOMER_PASSWORD`: dos cuentas customer técnicas distintas de la cuenta smoke, registradas por auth real únicamente en la copia. Root prepara sus secretos fuera de Git cuando el Preview esté autorizado; no se crean cuentas al listar tests o ejecutar selftests. Los ocho POST paralelos se distribuyen cuatro por cuenta para provocar contención real por tienda sin compartir el lock de cuota por cliente. Los reintentos comprueban el mismo pedido y referencia; las negativas usan tanto ID interno como referencia. El navegador aporta `X-Maui-Contract: 2` desde la app: el runner no lo añade a sus fetch. Los fixtures API sí hacen opt-in explícito.
- `e2e-fixture-ledger.private.json` conserva una cadena de estados por fixture/runId/stamp, registrada antes de mutar. Antes de repetir una corrida, la baseline original sigue íntegra por IDs privados (pedido, creación y audit, con versiones y fechas). Solo filas de tienda/producto efectivamente restauradas admiten aumento de `version`/`updated_at`, respaldado por el actor, campos, ventana temporal y secuencia continua de audit SQL del fixture. Se comparan íntegros sus campos de negocio; no se descarta metadata globalmente ni se reemplaza la baseline. Los checkpoints privados de pedidos propios de corridas anteriores también deben permanecer idénticos. Una corrida fallida requiere primero diagnosticar/restaurar y capturar su preservación; nunca reutilizar el ready consumido.
- Credenciales y bypass solo por entorno, nunca impresos: `SMOKE_CUSTOMER_PHONE`, `SMOKE_CUSTOMER_PASSWORD`, `SMOKE_STAFF_EMAIL`, `SMOKE_STAFF_PASSWORD`; `SMOKE_OWNER_EMAIL`/`SMOKE_OWNER_PASSWORD` si el personal no es owner; `SMOKE_OPERATOR_EMAIL`/`SMOKE_OPERATOR_PASSWORD` para los permisos negativos del operator (sin ellos queda un hallazgo); `SMOKE_BYPASS_TOKEN` (o `SMOKE_VERCEL_BYPASS`) para Previews protegidos (solo se envía al hostname del Preview).
- Solo Previews `*.vercel.app` (o loopback sin bypass para desarrollo local).
- Recepción permanente (PM-03): el runner **no abre la tienda** para pedir; los pedidos se registran con el horario real. Solo se restaura, al inicio, el override que dejó una corrida anterior interrumpida. Los escenarios fuera de atención (cierre manual y día sin atención con próxima apertura) cambian el horario por API owner como fixture técnico y lo restauran siempre.
- Los fixtures leen antes el producto de personal con su `version` real (el DTO público no la trae), registran valor previo y aplicado en `e2e-runtime.json` y restauran en orden inverso; solo revierten si el valor sigue siendo el que dejó el runner. Cada prueba de `@completo` parte de canasta vacía y sesiones vigentes, así que un fallo no oculta las demás.
- Contacto técnico temporal cuando falta el contacto del seed, cierre/stock y precio se registran antes de cambiarlos y se restauran incluso si falla el escenario. No se toca ningún pedido ajeno; quedan únicamente los pedidos propios para limpieza de root. Una interrupción de proceso puede impedir el `afterAll`: revisar `e2e-runtime.json` antes del reset o de continuar.

## Salidas saneadas (en `orquestacion-local/`, fuera de git)

- `e2e-runtime.json`: claves de idempotencia, IDs de pedido, snapshots acotados de fixtures técnicos, estado del override y hallazgos.
- `e2e-fixture-ledger.private.json`: historia privada de fixtures/restauraciones; no es un artifact publicable.
- `e2e-result.json`: resultado por prueba con errores saneados.
- `e2e-artifacts/`: capturas saneadas (nunca en login, con campos enmascarados).

Trazas, video y screenshots automáticos están desactivados: contienen red y formularios con credenciales. El service worker está permitido en ambos contextos. La cookie de Protection se prepara exclusivamente en el origen identificado antes de navegar, para cubrir también sus fetch públicos. WhatsApp se aborta: los enlaces `wa.me` se comprueban, no se abren.

429/503 son fallos de transporte controlados y acotados al POST del escenario; no acreditan políticas reales de rate limit o una caída real de Postgres. El timeout envía primero el POST real y retiene su respuesta 17 s (timeout del cliente: 15 s), verifica persistencia, recarga y reintenta con la misma clave. Chrome emula latencia/ancho de banda 3G sin reemplazar respuestas exitosas. El 401 revoca la sesión real por logout API. Ningún resultado local ni selftest sustituye la corrida completa sobre el Preview.

ME añade selección/persistencia de Efectivo, QR y Bre-B; referencia en PWA/admin/comprobantes/contacto; compatibilidad del DTO sin opt-in; lista de preparación, autosave/error/retry, pesos y marcas tras recarga; polling sobre un borrador del mismo ítem; cambio estructural pendiente; contacto sin decisión; sustitución/retiro; recogida y domicilio; reapertura permitida solo en Listo, versión obsoleta, permisos negativos y audit persistente. La referencia sirve como texto visible: para abrir una fila se usa su enlace existente con ID interno, sin exigir un filtro por consecutivo.

Los gates finales desde la raíz son `npm run ci:check` y, después de aprobarlo, `npm run ci:build`, con `VITE_DEMO_MODE=false`. Se ejecutan sobre el árbol final una vez cerrados los consumidores. La evidencia pública debe incluir SHA de la feature probada, deployment, scope aislado, resultados y digests de preservación; el SHA final de merge/deploy se registra aparte, junto a una comparación del árbol o una prueba sobre ese SHA. No publicar snapshots, IDs de filas humanas, cuentas, contraseñas, bypass, cuerpos de red ni trazas crudas.
